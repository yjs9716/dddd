## 1. 설계변수 (8개)

| # | 변수명 (SolidWorks 글로벌 변수명과 동일해야 함) | 범위 | 단위 |
|---|---|---|---|
| 1 | `input_thick` | 15 ~ 35 | mm |
| 2 | `input_angle` | 90 ~ 150 | deg |
| 3 | `power_input_thick` | 5 ~ 20 | mm |
| 4 | `power_output_thick` | 15 ~ 40 | mm |
| 5 | `mid_thick` | 15 ~ 35 | mm |
| 6 | `mid_angle` | 90 ~ 140 | deg |
| 7 | `mid_input_thick` | 15 ~ 35 | mm |
| 8 | `output_thick` | 15 ~ 35 | mm |

정의 위치: `OLHD.py`의 `PARAM_SPEC` **한 곳뿐**. 범위를 바꾸려면 여기만 수정하면
OLHD / ML / SolidWorks / result_parser가 전부 따라감.

### 유로 순환구조 (V1과 완전히 다름)

V1은 발열채널을 **1회만** 통과하는 단일 경로였지만, V2는 **분기 구조**임:

```
입구 → 하단(+X 방향, 8채널 1차 통과) → 분기 ┬→ 전원공급모듈 분기 ┐
                                             └→ 상단(−X 방향, 같은 8채널 2차 통과) ┴→ 합류 → 출구
```

- 총 유량(4LPM 고정)이 분기점에서 전원모듈 vs 상단패스로 갈림 (질량보존 → 한쪽이
  많이 가져가면 반대쪽은 필연적으로 적게 받는 관계)
- **핀뱅크 레인은 1차 통과 7개 + 2차 통과 7개 = 14개**. 두 통과는 분기 때문에
  평균 유속 자체가 다르므로 14개를 한 덩어리로 묶어 CV를 내면 "레인별 분배 불균일"과
  "통과별 유량 수준 차이"가 뒤섞임 → **통과별로 따로 CV를 내고 나쁜 쪽(max)** 을 사용
- 전원모듈 분기가 유량을 얼마나 가져가는지는 온도가 아니라 **유량비율**로 추적
  (단일 블록 온도는 단일점 절대값이라 블럭모델에서 신뢰도가 낮음 — 4절 참고)

## 2. V1 대비 무엇이 바뀌었나

### (1) 적응 샘플링: 격자 전수탐색 → Sobol 후보 샘플링 ★ 가장 중요

V1은 설계공간을 0.1단위 격자(301×251 = 75,551점)로 **전부 나열**해서 그 중
불확실성(σ) 최대점을 골랐음. 7차원에서는 같은 방식이면 후보 수가 천문학적이라
열거 자체가 불가능.

→ 매 회차 Sobol로 **32,768개 후보만 뽑아** σ를 평가하고 그 중 최대점을 선택.

### (2) 중복 제외: 정수 매칭 → 최소거리 기준

격자가 없어졌으므로 "이미 한 점"을 정확히 매칭할 수 없음.
→ 정규화 공간에서 기존 실험점과 거리 `MIN_DIST_NORM`(0.05) 미만이면 후보에서 제외.

### (3) 형상 미성립(리빌드 실패) 방어 ★ 신규

8변수 조합에서는 기하학적으로 성립 불가한 형상이 나올 수 있음.
V1에는 이 처리가 없어서 실패하면 캠페인 전체가 죽음.

→ 실패 시 `failed_v2.csv`에 기록하고 다음 점으로 진행.
→ DOE 진행은 "성공 수"가 아니라 **"시도 수"** 기준이라 같은 점 무한재시도 없음.
→ 실패점 근처는 이후 후보에서도 제외 (형상 미성립 가능성이 높은 영역이므로).
→ 연속 5회 실패 시 설정 문제로 보고 중단.

### (4) SolidWorks 변수명 불일치 감지 ★ 신규

V1의 `set_value`는 해당 이름의 수식을 못 찾아도 **조용히 넘어갔음**
→ 형상이 안 바뀐 채로 해석이 도는 사고가 가능한 구조였음.
→ V2는 없는 변수명이면 즉시 `KeyError`로 중단하고, 실제 존재하는 변수 목록을 출력.

### (5) 인터페이스 정리

- 파라미터를 8개 위치인자 대신 `dict`로 전달
- `result_parser.extract_and_save`가 튜플 대신 `dict` 반환 (목적함수 늘려도 호출부 안 깨짐)
- ML에 `current_idx()` 공개 함수 추가 (V1은 main에서 private `_load_results()`를 씀)

### (6) GPR 커널

- `length_scale` 8차원 ARD
- 상한 5.0 → **50.0**: 8변수 중 영향 없는 변수는 length_scale이 커지는 형태로
  드러나는데, 상한에 걸리면 "무관한 변수"를 식별할 수 없기 때문

### (7) 신규 진단 기능: `python ML.py`

학습된 ARD length_scale을 뽑아 **어떤 변수가 실제로 영향을 주는지** 출력.
8개 중 몇 개가 실제로 의미 있는지 보고, 다음 캠페인에서 변수를 줄일 근거로 사용.

```
=== 변수 영향도 (데이터 40점 기준) ===
[pressure_drop] length_scale (작을수록 영향 큼)
         input_thick:    1.403  ##############
         input_angle:   50.000  #      ← 상한 = 사실상 영향 없음
```

### 값이 정의된 위치 (단일 출처)

같은 값이 두 파일에 각각 하드코딩돼 있으면 한쪽만 고쳤을 때 조용히 어긋나므로,
아래 값들은 **한 곳에서만 정의하고 나머지가 import** 해서 씀:

| 값 | 정의 위치 | 쓰는 곳 |
|---|---|---|
| 설계변수 이름·범위 (`PARAM_SPEC`) | `OLHD.py` | ML / Solidworks / result_parser |
| DOE 점 수 (`DEFAULT_N_DOE` = 10 × 변수수) | `OLHD.py` | `ML.N_DOE` |
| 발열채널·레인 개수 (`N_SOURCE`, `N_LANE`) | `icepak.py` | `result_parser`의 CSV 행 인덱스 |
| PAO 밀도 (`PAO_DENSITY`) | `icepak.py` | `result_parser`의 중량 계산 |

> 변수를 추가/삭제하면 `PARAM_SPEC`만 고치면 DOE 점 수까지 자동으로 따라감.
> 채널·레인 개수를 바꾸면 `icepak.py` 상단만 고치면 파싱 행 인덱스가 자동으로 따라감.

### `icepak.py` 인터페이스 계약 ★ 스크립트를 다시 뽑을 때 이것만 지키면 됨

**함수 시그니처** (다른 파일들이 이 형태로 호출함, `main.py` 참고):

```python
def connect_aedt():
    ...
    return desktop, None          # ipk는 아직 없으니 None

def run_icepak(desktop, ipk, step_file, idx, params):
    ...
    return ipk, result_path, pao_volume_mm3
    #   result_path    : 이번 idx의 CSV 저장 경로
    #   pao_volume_mm3 : PAO_Separate1.volume — 중량 계산엔 안 쓰고 교차검증 로그용
    #                    (실제 중량은 SolidWorks 값만으로 계산 — 4-(6)절 참고)
```

`params`를 받는 이유: 전원모듈 입구 측정면(`Rectangle1`)의 Height가 설계변수
`power_input_thick`에 따라 매번 달라지기 때문.

**CSV 출력 행 구조** (`result_parser.py`가 `skiprows=5` 이후로 이 순서를 그대로 기대함 —
Fields Summary에 `Calculation:=` 추가한 순서 = CSV 행 순서):

| 행 | 내용 | 쓰는 열 |
|---|---|---|
| 0~7 | source01~08 온도 | Max(8) → `max_temp`, Mean(9) → `temp_std` |
| 8 | Fan1_Passage 차압 | Mean(9) |
| 9~15 | V_inlet_01~07 (1차 통과) 속도 | Mean(9) × Area(11) |
| 16~22 | V_inlet2_01~07 (2차 통과) 속도 | Mean(9) × Area(11) |
| 23 | Rectangle1 (전원모듈 분기 입구) 법선방향 속도 | Mean(9) × Area(11) |

**열 인덱스** (실제 export 파일로 검증 완료):

```
0 Entity Type  1 Geometry Type  2 Entity  3 Quantity  4 Side  5 Normal  6 Mesh
7 Min  8 Max  9 Mean  10 Stdev  11 Area/Volume  (12 Variation)
```

- `Area/Volume`(11)은 겸용 열이지만, 모든 `Calculation`이 `Object/Surface`라 **항상 면적(m²)**.
  `"5.51786e-05 m^2"`처럼 단위 문자열이 붙어 나오므로 숫자만 떼어 씀
- GUI 표에 보이는 `Total` 열은 실제 export 파일엔 없음 → 맨 뒤 `Variation` 위치가 12
- 구분자가 콤마/탭 중 무엇으로 나올지 버전마다 다를 수 있어
  `result_parser`가 `sep=None, engine="python"`으로 자동 인식함

**전원모듈 유량을 속도로 재는 이유** ★
`VolumeFlowRate`로 걸면 Icepak이 유량을 계산하지 않고 면적(m²)만 돌려줌.
같은 면에 `Speed` + 법선방향벡터 + `Reduced`로 걸면 정상 동작하므로, 이렇게 우회함:

```
Q = (법선방향 속도의 면적가중평균) x 단면적
```

면적가중평균의 정의가 (적분 / 면적)이라, 다시 면적을 곱하면 적분값이 그대로 복원됨 →
**근사가 아니라 정확히 같은 값**.

**면적은 반드시 CSV의 `Area/Volume` 열 실측값을 쓸 것** ★
도면상 치수(`8mm × power_input_thick`)로 계산하면 안 됨. Fields Summary는 CAD 면이 아니라
**메시에 투영된 면**에서 값을 뽑기 때문에, 측정면이 셀 경계에 딱 안 맞으면 보고되는 면적이
도면값과 어긋남 (실측: 40mm 두께에서는 정확히 일치했지만 5mm에서는 40mm² → 50.95mm²로 27% 초과).
DOE는 0.1mm 단위 값을 넣으므로 이 어긋남이 캠페인 중 조용히 발생할 수 있음.

**레인 CV도 속도가 아니라 유량 기준** ★
같은 이유로, 레인별 대표값을 속도 `Mean`으로 쓰면 안 됨:

```
Mean 단독   = ∫v·dA / Area    ← 벽면(속도≈0) 셀이 면적에 섞이면 값이 희석됨 (레인마다 다르게 왜곡)
Mean × Area = ∫v·dA           ← 속도 0인 영역은 0을 기여하므로 왜곡이 상쇄됨
```

실측에서도 면적이 8% 부풀었던 레인 하나가 속도 기준으로는 혼자 튀었는데,
유량 기준으로 바꾸니 그 이상치가 크게 완화됐음 (1차 통과 CV 9.61% → 9.43%).

> **측정면 배치 원칙**: 유로 단면을 **전부 덮되(살짝 넘쳐도 무방)**, 모자라게 잡지 말 것.
> 넘친 부분은 속도 0이라 적분에 0을 기여해 자동 상쇄되지만, 모자라면 실제 유량이
> 빠진 채로 적분되어 과소평가가 그대로 남음. 단, **옆 유로까지 넘어가면 안 됨**(거긴 0이 아님).
> 경계면에 걸치는 것보다 유로 안쪽으로 넣는 편이 메시가 깨끗하게 잡힘.

**2차 통과 속도의 부호**: 유동 방향이 반대라 법선성분 평균이 음수로 잡힐 수 있음.
CV 계산 시 부호가 뒤집히면 `max()` 비교가 무의미해지므로 `result_parser`가 절대값을 씀.

## 4. 반입 전 확인 필요 ⚠

`input_angle`, `mid_angle`을 mm로 주셨는데 값(90~150)으로 보아 **deg**로 간주하고 작성함.
맞는지 확인 필요.

### (2) SolidWorks 글로벌 변수명
V1은 한글(`각도`, `유로두께`)이었는데 V2는 영문명으로 작성함.
**Equation Manager의 실제 변수명과 철자가 정확히 일치**해야 함.
(불일치 시 첫 실행에서 바로 KeyError로 알려주므로 조용히 잘못 도는 일은 없음)

| 항목 | 상태 |
|---|---|
| `Fan1_Passage` | 차압 항목이 리코더본에 빠져 있어 V1 설정으로 복원함 → **실제 export에서 정상 출력 확인 완료** |

| `Block1` 발열 | source01~08 합쳐서 `Total Power 40W`. 전원공급모듈 발열체는 이번 형상에 **없음**(온도를 보지 않기로 해서 유량만 측정) |

### (4) 메시 크기 — 검증용/실전용 구분 ★

`icepak.py` 상단 상수로 노출돼 있어 코드를 뒤질 필요 없이 여기만 바꾸면 됨:

```python
MESH_REGION_X/Y/Z = 2.0 / 1.0 / 1.0   # SubRegion(유체 도메인) 로컬 메시
GLOBAL_MESH_X/Y/Z = 2.0 / 2.0 / 2.0   # 전체 Region 글로벌 메시
```

- 코드 흐름만 빠르게 확인할 땐 크게(거칠게) 잡아도 되지만,
  **실제 캠페인은 반드시 위 값(또는 더 촘촘하게)으로 되돌릴 것**
- 거친 메시에서는 얇은 두께 구간(`power_input_thick` 하한 근처)에서 측정면이 셀 경계에
  스냅되면서 면적·유량이 틀어질 수 있음

### (5) 초기 DOE 점 수 = 80
`10 × 변수수` 경험칙 기준(8변수) — `OLHD.DEFAULT_N_DOE`가 변수 개수에서 자동 계산하고
`ML.N_DOE`가 이를 그대로 씀. 실행 1회당 SolidWorks 리빌드 + Icepak 풀 해석이므로
**시간 예산 확인 필요**. 줄이려면 `ML.py`의 `N_DOE`에 숫자를 직접 넣으면 됨.

### (6) 목적함수 — 확정 (4개)

| # | 목적함수 | 방향 | 비고 |
|---|---|---|---|
| 1 | `pressure_drop` (차압) | 최소화 | log 변환 |
| 2 | `vel_cv` (핀뱅크 레인 속도CV) | 최소화 | `max(1차 통과 CV, 2차 통과 CV)` — 레인 간(Y축) 유량분배 균일도 |
| 3 | `temp_std` (8채널 온도표준편차) | 최소화 | 유동방향을 따라가며 물이 데워지는 예열 효과. `vel_cv`와 보는 축이 달라 중복 아님 |
| 4 | `max_temp` (8채널 최고온도) | 최소화 | V2는 데워진 물이 같은 채널로 재진입하는 구조라, 방열핀을 건드리지 않아도 유로 형상만으로 온도가 크게 움직일 수 있어 목적함수로 채택 |

**제약조건용 지표** — GPR 학습·예측(`pred_*`)은 목적함수와 똑같이 하지만,
적응샘플링 방향과 종료판정에는 관여하지 않음:

| 지표 | 용도 |
|---|---|
| `power_module_flow` | 전원모듈 분기 유량비율 (0~1). "몇 % 이내" 조건으로 후보 필터링 |
| `weight` | 알루미늄 + PAO 총 중량 [kg]. "몇 kg 이하" 조건으로 후보 필터링 |

- 제약조건도 **GPR 학습이 반드시 필요**함. 유전알고리즘 단계에서 실측 없이
  "이 후보가 조건을 만족하는가"를 걸러내야 하므로 예측값이 있어야 하기 때문.
  필터링할 때는 예측 평균이 아니라 **평균 + kσ**(불확실성 마진)로 보수적으로 거는 것이 안전.
- **`max_temp`는 단일 극값이라 노이즈가 큼** — 여러 값을 평균 내는 지표와 달리 오차가
  상쇄되지 않아, 예측오차가 `ERR_THRESHOLD` 아래로 안 내려가서 캠페인이 종료조건을
  계속 못 만족할 수 있음. 그럴 때는 `ML.py`의 `TERMINATION_NAMES`에서 `"max_temp"` 하나만
  빼면 됨 (빼도 GPR 학습·예측·적응샘플링에는 그대로 참여).
- `ML.py`의 `OBJECTIVES` / `CONSTRAINTS` / `TERMINATION_NAMES` 리스트만 고치면
  다른 조합으로도 바로 바꿀 수 있게 만들어둠.

### (7) 중량 계산 방식

Icepak 없이 **SolidWorks 값만으로** 계산함 (PAO를 채우는 박스가 고정 크기라
"고정 부피 − 알루미늄 부피 = PAO 부피"가 항상 성립하기 때문):

```
PAO 부피 = FULL_SOLID_VOLUME_MM3(2341073.1, 채널 없이 완전히 채워진 형상 부피, 상수)
           − 알루미늄 부피(SolidWorks, 매 idx 리빌드된 실제 형상)
weight  = 알루미늄 질량 + PAO 부피 x 794 kg/m^3
```

- `Solidworks.update_sw`가 리빌드 직후 `(알루미늄 질량, 알루미늄 부피)`를 반환
  → `main.py`가 그대로 `result_parser.extract_and_save`로 전달
- `icepak.run_icepak`이 반환하는 `pao_volume_mm3`(Icepak `PAO_Separate1.volume`)는
  중량 계산엔 안 쓰고, 위 상수 기반 계산과 크게 어긋나는지 보는 **교차검증 로그**로만 사용
- ⚠ `FULL_SOLID_VOLUME_MM3`은 plate/plate_base **바깥 둘레 치수가 고정**이라는 전제의 상수.
  8개 설계변수는 전부 내부 유로만 바꾸므로 영향 없음 — 만약 바깥 윤곽 자체를 바꾸는
  변수가 추가되면 이 상수도 다시 재야 함

**질량/부피를 뽑는 SolidWorks API**: `asm.Extension.CreateMassProperty()`(최신 방식)는
이 환경에서 `Extension`이 깨진 COM 프록시로 반환되어(win32com dynamic dispatch 한계로 추정)
동작하지 않았음. 대신 구버전 API인 `asm.GetMassProperties`(괄호 없이 속성으로 접근)를 쓰는데,
반환되는 12개 튜플의 순서가 문서화되어 있지 않아 SolidWorks GUI의 Mass Properties 패널
값과 하나씩 대조해서 확정함: `[0:3]`=무게중심(m), **`[3]`=부피(m³)**, `[4]`=표면적(m²),
**`[5]`=질량(kg)**, `[6:12]`=관성모멘트 Lxx,Lyy,Lzz,Lxy,Lxz,Lyz(kg·m²).

**검산 예시** (알루미늄 밀도는 기준 형상에서 역산한 2700 kg/m³):

```
알루미늄 부피 1,655,878.1 mm³
  → 알루미늄 질량 4.470871 kg
  → PAO 부피 (2,341,073.1 − 1,655,878.1) = 685,195.0 mm³ → 0.544045 kg
  → 총 중량 5.014916 kg      (엑셀 수기 계산값과 소수점까지 일치)
```

## 6. GPR 이후 단계 (참고 — 아직 코드화 안 함)

1. 이 캠페인으로 목적함수 4개 + 제약조건 2개의 GPR 지도를 **전역에 걸쳐 고르게** 완성
   (지금 코드가 하는 일)
2. 완성된 GPR 지도 위에서 유전알고리즘(NSGA-II 등)으로 파레토 프론트 탐색
   (실측이 아니라 GPR 예측값으로 도니까 비용이 거의 안 듦)
   - **제약조건 필터를 먼저 걸고** 파레토를 계산: 예) "전원모듈 유량비율 X% 이내",
     "중량 Y kg 이하". 필터는 예측 평균이 아니라 **평균 + kσ**로 보수적으로
   - 남은 후보들에 대해 목적함수 4개로 파레토 프론트 도출
3. 파레토 후보군에서 최종 1개 선택 — 우선순위 방식(예: `max_temp`가 전역 최솟값 대비
   일정 밴드 안인 것들을 먼저 추리고, 그 안에서 나머지 비교)을 쓸 수도 있음.
   밴드를 너무 좁게 잡으면 노이즈를 최적점으로 착각할 위험이 커짐
4. 최종 후보 몇 개는 **반드시 실제 SolidWorks+Icepak으로 재검증**
   — 서로게이트 모델의 빈 구멍(데이터 없는 지역)을 최적점으로 착각할 수 있기 때문
   - 재검증 결과가 예측과 크게 어긋나도 실패가 아님. 그 실측값을 `results_v2.csv`에
     추가해 GPR을 재학습하면 **바로 그 지점의 불확실성이 줄어듦** → 2~3단계 재실행

**왜 전역을 고르게 매핑하는 게 먼저인가**: 유전알고리즘이 GPR 지도 위 어디를 뒤지든
그 지점이 실측으로 뒷받침돼 있어야 안전함. 처음부터 "파레토 프론트 근처만" 편향
샘플링(EHVI 등)하면 샘플은 아끼지만, 초반에 파레토 위치를 잘못 짚었을 때 그 바깥은
아예 안 가봐서 유전알고리즘이 잘못된 확신에 빠질 위험이 더 큼.

## 9. 남은 이슈

### `power_input_thick` 범위 재검토 (보류 중)

현재 범위 5~20mm는 **측정면을 고치기 전의 잘못된 유량값**을 근거로 좁힌 것.
측정면 수정 후 같은 5mm에서 11.5% → **21.2%** 로 약 2배 차이가 났으므로,
10mm·40mm 시점의 값도 같은 오차를 포함하고 있음.

- 범위 전체가 이미 20%를 넘길 가능성이 있어, `power_module_flow` 제약을 낮게(예: 15% 이내)
  걸면 **만족하는 후보가 하나도 안 남을 수 있음**
- 확인하려면 상한(20mm)에서 한 점만 다시 재보면 됨
- 다만 분기 비율은 `power_input_thick` 단독이 아니라 `power_output_thick`(직렬),
  `mid_thick`(경쟁 경로)의 조합으로 결정되므로, 한 점만 보고 범위를 성급히 좁히면
  "입구는 얇지만 출구도 좁아 균형이 좋은" 조합까지 잘려나갈 수 있음
  → 지도를 그려서 판단하는 게 이번 캠페인의 목적이기도 함
